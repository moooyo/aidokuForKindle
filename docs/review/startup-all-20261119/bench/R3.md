# R3 launcher benchmark audit

Run `analyze_v3.py` on `test-env` with Python 3.11 or later. This tool only
reads retained batches and creates reports or host-only plans. The designated
device operator uses the frozen runner separately. The R1 and R2 tools and
their results remain unchanged.

The audit pins the final producer receipt, unchanged compiled source manifest,
ARM application, new raw launcher, and ARM portrait helper. It checks the
installed control identities and shared native query backend from the frozen
device guards, and verifies the recovered original launcher backup. It also
recomputes the private launcher's exact trace instrumentation and checks every
member of the original payload, including the bridge and persistent option
files. No new ELF, launcher, environment override, arguments, or unrelated
settings can substitute for this composition.

The [handoff](../../../../HANDOFF.md) identifies the worker inventory. Set
`WARM_BATCH` and `COLD_BATCH` to the directories of its completed default
timing plans. The following commands replay those records off-device:

```sh
root=/root/aidoku-all-bench-20261119
python3 -B -I "$root/tools/analyze_v3.py" analyze \
  --batch "$WARM_BATCH" \
  --trial combined --workload warm --phase screen --output /tmp/r3-warm.json
python3 -B -I "$root/tools/analyze_v3.py" analyze \
  --batch "$COLD_BATCH" \
  --trial combined --workload cold --phase screen --output /tmp/r3-cold.json
```

The default guard requires six complete alternating pairs per regime and no
more than 50 ms median paired regression in either usable or covers. Savings
are baseline minus candidate, in milliseconds. These observations measure
software and driver events after an indexed native request; they are not
optical timing or promotion approval.

Both regimes passed the median guard. The complete observations, including
the slow cold pair, remain in `$root/reports/v3-default-w.json` and
`$root/reports/v3-default-c.json`. The R2 tool's rejection of the new launcher
is retained as `$root/reports/v3-default-w-rejected-by-r2.json`.

For `layout`, `prewarm`, `grace`, and `supervisor`, use `--workload warm` and
the respective `--trial`. The two arms use identical R3 programs and differ
only in that trial's persistent setting. `--qualification-batch` binds a
separate native pixel qualification to the same arms. The existing screen
and confirmation thresholds remain in force; a screen is not confirmation.

To prepare the all-options qualification, pass the frozen R3 warm
`plan.json` to `prepare-all-options --release-plan`. Audit the completed run
with `analyze-all-options --batch <batch> --release-plan <default-plan>
--output <report>`. Both arms use the same R3 files and the comparison changes
the six persistent values together. The report carries no latency result.
