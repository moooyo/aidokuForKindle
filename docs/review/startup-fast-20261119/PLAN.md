# Faster Library startup: evaluation contract

Control: installed R3 application `1b1c508e`, launcher `412163f1`, portrait
helper `bde28cd5`. The previous [normal Library tile measurement](../startup-entry-timing-20261119/README.md)
is context, not the control arm for a new candidate. Product code is based on
`3d8f0d7` (same R3 product inputs).

- Measure the real native Library tile when its view and unique artwork are
  identified; otherwise explicitly label a run as native indexed URI dispatch.
  Do not combine trigger types, warm and empty caches, pilots and screens, or
  distinct candidate tuples. Use a staged copy of library settings/data. The
  harness temporarily swaps the installed launcher for a guarded routing
  script, then must restore its original contents and metadata. Do not clear
  the user's cache, replace the installed application, or leave the candidate
  on the device.
- Warm: time to the first submitted Library frame with software input ready,
  and to the frame with all seven cover slots for six local books. Empty
  derived-thumbnail cache: complete covers are primary; first usable remains
  a guard. A loading screen or an attached-but-still-booting controller
  does not count. Neither endpoint measures optical completion.
- For an initial screen, use six balanced pairs per regime and retain every
  completed pair, favorable or not. A two-pair pilot is diagnostic only.
  Treat a median paired saving of at least 100 ms with five of six wins
  and no more than 50 ms median regression on the other endpoint as a
  promising screen, not proof. Independent confirmation requires ten new
  pairs and nine wins. The current harness supports only the pilot and the
  six-pair screen; a confirmation plan and analyzer must be prepared and
  verified separately. As a practical target for this work, call a change
  substantial at 300 ms on warm usable startup or 1 s on empty-cache complete
  covers. A missed target should remain visible.
- Check the device body and observable right status pixels independently of
  the timing, verify identical options/inputs, and check process lifecycle,
  display/input ownership, restoration and owner/token release. Host image
  parity or faster individual kernels alone do not establish device speed.
  Do not change validation, input gating, image quality, or release policy to
  make a timing test pass. No automatic daily-driver promotion.

The [November 21 follow-up](../startup-followup-20261121/README.md) adds a
separate ten-pair confirmation plan and analyzer for the eligible staged
empty-cache candidate. It does not change this original screen or its clocks.
