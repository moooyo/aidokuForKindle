# Managed foreground pilot

This is a new, hands-off diagnostic, **not an indexed URI, native tile,
optical latency or promotion study**. It starts immediately before invoking
each staged production launcher with `--foreground` and the managed-Library
environment. Both sides use the same minimal tracing arguments. The baseline
copies the current installed app and its helper; the candidate uses the
corrected ARM build. The installed launcher must match the R3 Git bytes.
No installed entry is replaced and no real library or cache is used.

The desktop application imports six deterministic synthetic JPEG books into
a staged path in a private mount namespace. Both workloads use the same
8,961,303 encoded bytes. On hardware each case starts with a new copy of the
same synthetic database. Empty cases have no derived cache. Warm cases start
from copies of one cache primed on the device by the control.

Freeze one plan per regime. Use one fresh host owner/token lease per batch,
only after the plan, upload, programs and independent analysis are ready.
After a warmup on each arm, run **AB then BA**; retain both pairs. Take an
independent software screenshot and live framebuffer sample on each arm
outside the timing cases. Require six observed cache hits or misses, seven
presented cover slots, the first checked full-frame input fence, monotonic
frame markers and settled output. Compare the body below the clock and the
observable right status area for both capture types. Shell request timestamps
have 10 ms resolution. A failed gate stays visible; two pairs cannot
establish a sustained speedup.

Only the staged GUI can be signaled during cleanup. Check stock app, power,
window manager, launcher locks, lights, protected file metadata and stock
body restoration. Retrieve only synthetic case evidence, remove the stage
and release before analysis. The initial stock frame never leaves the
Kindle. Do not retry an operated plan as though it never ran.

The rebuilt lab reported stock portrait rotation 1 with a double-height
virtual framebuffer; the historical tile study required rotation 3. For
this separate pilot, read the active page from the kernel's pan offset,
verify unchanged geometry across the read, and normalize by the application's
reported portrait rotation. Before comparing either pixel region, require
the aligned grayscale layout (64×80 area averages) to agree with its own
software picture within 12 gray levels mean error, and the inverted layout
to score at least 3 gray levels worse. For stock restoration compare the
central rows, excluding 72 rows at both ends to avoid the stock clock in
either portrait direction.

After both post-SEND pilots closed, the same post-SEND candidate was selected
without rebuilding for a separate follow-up screen. `freeze.py both --mode
screen` takes **six new alternating pairs per regime**, plus separate warmups
and pictures; none of the pilot observations enter this cohort. Prespecified
primary is usable Library startup for warm and complete covers for cold. Report
all six paired differences, wins and median. Require at least 100 ms median
saving, five wins and at most 50 ms median regression on the other endpoint,
in addition to all case, picture and recovery checks, to call a *staged*
screen promising. The practical targets remain 300 ms and 1 s respectively;
neither a promising staged screen nor these practical targets identify
native-tile latency or authorize release.

The cold screen alone qualified for an independent confirmation. Keep its
post-SEND program files unchanged and freeze a new, empty batch with
`freeze.py cold --mode confirmation`. Both arms warm up, then complete ten
new alternating pairs, five in each order. The two independent picture
visits follow the timed cases. Do not mix in earlier visits, replace a
failed case, or repeat the warm screen. Record the whole operation sequence
and owner-checked release. Confirm a staged cold benefit only with at least
nine strictly faster complete-cover pairs, a median paired saving of at
least 100 ms, and a median usable-frame regression no worse than 50 ms.
Report the 1 s practical target independently. The six warm screen pairs
remain the existing warm guard for this unchanged candidate, not a confirmed
warm gain. The staged protocol neither reads nor modifies WeRead's installed
launcher; it checks for active projects and launcher locks before entry.
