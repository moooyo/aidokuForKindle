# What the draw-accounting visits represent

**The card is ordinary; the executable's file lifetime is not.** Treat this as a measurement of the diagnostic binary launched through the normal card with the installed Library data, not as a measurement of repeated opens of the installed R3 executable. The excluded warmup is useful for checking the measurement path, not for increasing the formal sample size.

## Why identical bytes do not mean a warm executable

The [freezer](freeze.py) seals one archive. For each visit the [inherited host runner](../../startup-jpeg-native-20261122/host.py) uses a new label. The [device runner](../../startup-jpeg-native-20261122/device.sh) requires an absent stage, creates it, and extracts the archive there. The [selector](../../startup-jpeg-native-20261122/selector.sh) bind-mounts only that visit's `programs/selected-app` on the normal executable path. It does not copy the file by binding it, replace the production launcher, or change another application's entry. Restore removes the bind; close and the independent absence check retire that visit's directories. The next launch is a new process backed by a newly created file, even if a filesystem later recycles an inode number. The observed app is **53,738,400 bytes**, not 53 MB of fonts.

A bind mount re-exposes the underlying file. It does not provide a new cache for that file, nor does it give the next newly extracted file the removed file's page-cache identity. Conversely, it is **not a controlled cold-cache experiment**: extraction writes the bytes, verification can read them, and the kernel can retain or reclaim pages. Transferring and extracting the whole fixture can also perturb memory and storage, even though that work is before the card timer. The current protocol neither measures residency immediately before `exec` nor flushes any caches. Persistent installed bytes, the app's metadata/thumbnail cache, per-process page tables and in-process glyph caches are different things. See the [Linux VFS page-cache model](https://docs.kernel.org/filesystems/vfs.html).

The [build script](../../../../build.rs) expands bundled font sources at build time. [Startup registration](../../../../src/bootstrap_fonts.rs) passes static `include_bytes!` slices to the font collection without inflating or copying all of them at launch. Font registration is not proof that every later-needed font page is resident. The ELF also contains code and other data. Nothing in the draw line records a faulting address, mapped object, thread wait reason, I/O queue, number of bytes read, or fault duration.

## Reading the counters

The excluded warmup had roughly 815 ms elapsed, 96 ms of GUI-thread CPU, 140 major faults and 141 voluntary switches during this draw. The roughly 719 ms difference is a **non-CPU residual**, not 719 ms of font I/O or scheduler delay. CPU and wall are sampled in slightly different nested intervals. The faults and switches apply to this thread, but their nearly equal counts do not pair them. A major fault indicates a fault requiring I/O; a voluntary switch is not specific to storage. The counters cannot distinguish executable code, bundled font data, another mapped file or swap; distinguish a read from device or filesystem queueing; or separate runnable wait from blocking on another thread. They are not one page, one read or one time interval per count. See [`getrusage(2)`](https://man7.org/linux/man-pages/man2/getrusage.2.html). Do not infer that glyph rasterization is the cause, that all delay is removable, or that the full card-to-Library interval equals the draw. Do not prescribe font restructuring, whole-ELF read-ahead/`madvise`, pinning memory, clearing system caches or changing power policy on this evidence.

## Smallest useful follow-up, if requested separately

1. **Daily-driver relevance first.** Reuse the [unchanged-R3 external observer](../../startup-followup-20261121/rendered-library/README.md) for normal new-process opens of the same installed file. It measures a *release-to-visible-Library upper bound*, not this draw's CPU or fault count. Existing evidence may already answer whether the user-visible delay warrants another diagnostic. Never compare this bound to a diagnostic callback as if they were the same endpoint. A resident resume is a different path: it keeps a process and its glyphs/page tables, and may not issue a new startup frame.
2. **If file identity is the specific question,** the minimal controlled extension is two immediate ordinary-card opens per prepared stage, using the *same diagnostic file/bytes and same measurement*, with two verified, different GUI process births. Complete normal exit and verify stock state between opens; unbind/rebind the same privately owned source if necessary. Compare the first and second draws within the pair. This estimates the change on reopening the same file **plus other natural warming/order effects**, not isolated font-fault latency. To test file-identity specificity, pre-stage two byte-identical files under identical load/age conditions and counterbalance second-open same-source versus other-source across fresh blocks; record uncertainty and both orders. No forced cache invalidation, inode-number guessing or whole-file scans between timed opens.
3. The existing one-visit protocol **does not authorize that extension**. It would require a new tightly bounded, preflighted, continuous-use lease plan, same-source ownership checks, fresh per-open process/log binding, and verified restoration/absence of every mount and file before release. Do not leave a bind, helper, retained test file, or registration change across unrelated leases; never hold the device waiting. Do not alter the installed data, WeRead/BiliComics entries or stock registration. If safe restoration or two immediate opens cannot be assured, keep the current conclusions and do not run it.
