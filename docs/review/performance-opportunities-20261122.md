# Next performance experiments: Library startup and Reader turns

November 22, 2026. Source reviewed: `a38b9b3`. The last verified daily Scribe installation is [R3, `8baf57f`](../../HANDOFF.md); it is not the current checkout. The new experiments ran on `test-env`. The Scribe timings below come from **existing** device visits. No production code, display policy or installation was changed, and no Kindle lease was used.

**Decision:** put prepared-turn source verification first for Reader. Cache size also affects the first visible Library on both desktop layouts: 10,000 indexed files added about 20–24 ms compared with an empty cache. Reusing the reconciliation query is therefore worth pursuing **for large offline caches**, not as a fix for the daily six-book shelf. Its isolated host gain is measured; its card-to-Library gain is not. Keep R3 installed.

## Reader: what remains after a prefetch hit

The [three original Perf05 traces](tab-perf05-20261116/traces/final) were replayed on `test-env`: join action and request IDs, require successful traces with no dropped events, and match framebuffer write and accepted SEND on the same frame sequence. This is the **November 16 Scribe**, eight distinct 2480 × 3508 PNGs, Fast mode, crop and two-page layout. It is not a new HEAD run, the default Normal mode, or a physical KPW6 result. The timer starts when the app receives the scripted pointer-derived action; SEND means the driver accepted the update, not that the ink settled. See the [original trial](../TAB_FEEDBACK_AND_PERF05_20261116.md) and [measurement boundaries](../READER_E2E_MEASUREMENT.md).

| Prepared forward turns | Delivered | Action to SEND, median | Source verification per turn | Median share of that same turn | UI ready to SEND per turn |
| --- | ---: | ---: | ---: | ---: | ---: |
| First visit | 3 | 139.685 ms | 63.438–65.435 ms | 45.9% | 49.421–53.655 ms |
| Repeated visit | 3 | 137.699 ms | 62.239–64.710 ms | 46.5% | 49.639–61.314 ms |

**1. Make prepared-frame verification cheaper without showing stale pixels.** The [prepared worker](../../src/app/reader_pipeline.rs#L568) verifies both sources serially. [SourceProof](../../src/render_cache.rs#L224) rechecks page identity and the named path around [content verification](../../src/cache.rs#L1214). For an external original, the hot path reads the entire file **once** per page. It is not decoding the PNG again. Local CBZ entries live under USB-exposed `data/local/content`, outside the shared artifact cache: an app-created version directory is not proof that another writer cannot replace its contents. A managed download and a local import of the same picture are useful controls.

First separate path/metadata, file read and digest time. One candidate for a cold-built next frame is to retain the **exact encoded bytes used to produce its pixels**, then compare a fresh read of the named file against them, chunk by chunk through EOF, rather than computing a new digest. Only keep bytes already available during prefetch; charge their allocation to the existing **32 MiB** next-frame budget and fall back to the current proof when unavailable. Recheck aliases, changes, generation, cancellation and the manifest as today. Test same-length edits and truncation, not just unchanged images. This exchanges CPU for retained memory and still reads the current file; the measured 62–65 ms is **not** a promised saving. The historical [slot peak](tab-perf05-20261116/traces/final/perf05-steady.state.json#L476) was 9,791,040 bytes for this book, not a general RSS bound.

**Host screen of the content check.** On `test-env` we compared the production-style `sha2` 0.10.9 streaming digest against an independently owned byte snapshot. Both arms opened the current file and read in 64 KiB chunks, with identical before/after canonical-path and file-metadata checks. This was a release x86_64 benchmark of two distinct **synthetic payloads**, not a decode of the Perf05 book or the entire `SourceProof`/publication path. Per size: one warmup per arm, 24 alternating AB/BA pairs in one process, warm OS caches, two files verified serially per observation. Extra retention excludes the common read buffer.

| Payload per page | Digest median per spread | Exact comparison median per spread | Paired median saving | Faster pairs | Extra retained bytes |
| --- | ---: | ---: | ---: | ---: | ---: |
| 1 MiB | 0.910 ms | 0.067 ms | 0.842 ms | 24/24 | 2 MiB |
| 4 MiB | 3.671 ms | 0.520 ms | 3.153 ms | 24/24 | 8 MiB |

Both rejected a same-size last-byte edit, a truncation and an append. There was no measurement of memory pressure, slot admission, changed-path races, device storage or complete turns in this screen. A lower-memory alternative is to benchmark a different implementation of the **same** digest. The [locked digest implementation](https://docs.rs/sha2/0.10.9/src/sha2/sha256.rs.html) selects different backends on x86 and 32-bit ARM; neither these milliseconds nor their ratio predict the Scribe outcome.

**2. Avoid discarding a matching in-progress next frame.** [A new request cancels prefetch](../../src/app/reader_pipeline.rs#L325), and the [fast path accepts only a ready slot](../../src/app/reader_pipeline.rs#L538). In the 600 ms burst trace, one foreground request reached worker completion 584.550 ms after its action but never published; the later delivered turn took 230.469 ms. This is evidence of supersession, **not** proof that matching prefetch existed on that tap or that 585 ms can be saved. Log the target and state at each tap (empty, preparing for this target, ready, different target). If matches are common, let only an exact match finish at interactive priority; advance the desired generation safely and reject wrong targets after a seek, reversal, layout change or sleep. Keep one decoder and one next-frame slot. Count unpublished requests as well as delivered turns.

**3. Profile cold spreads before choosing an image kernel.** The [unprepared open](tab-perf05-20261116/comparison.json#L652) took 1,154.647 ms and the [burst seek](tab-perf05-20261116/comparison.json#L867) took 1,163.162 ms. In the open, the two sequential render calls were 488.375 and 521.708 ms; the two source-fetch calls were under 1 ms each. Render includes source checks/reads, decoding and pixel processing, not just PNG decompression. Split [external-source passes](../../src/render_cache.rs#L1206), decoder wait, decode, crop, Triangle resize and dither before changing any of them. Do not add an unbounded second decoder or re-enable hardware PNG: the [same-picture Scribe trial](../KINDLE_MEDIA_ACCELERATION.md#L198) found hardware plus CPU resize slower than software. On a prepared turn the UI pixel preparation was already about 0.01 ms; if verification improves, distinguish scene drawing, previous-frame wait, actual write and SEND before optimizing display. Do not change waveforms or remove the wait to improve a software timestamp.

## Startup: ordinary shelf versus large offline cache

**Ordinary card opens.** The [unchanged R3](startup-followup-20261121/rendered-library/README.md#L17) reached a framebuffer match for Library entries and navigation at a median **upper bound of 2.399 s** (three launches of the six-book shelf, 120 ms observation interval, caches not cleared). Covers were not required. A [different diagnostic cohort](startup-release-draw-20261122/README.md#L5) measured card release to the accepted Library frame at **2.960 s** (three formal launches). Its first business draw took **623.075 ms wall** and **96.852 ms GUI-thread CPU** at their respective medians. The three draws each had 140 major faults. The diagnostic unpacked a **new executable file for each visit**. A [fault count](https://man7.org/linux/man-pages/man2/getrusage.2.html) is not a fault duration; it does not tell us which file caused the wait. The two cohorts and endpoints are not a before/after comparison.

**Decision for this shelf: do not prioritize a faster cache open as the first-screen fix.** In a third, independent [three-launch transition cohort](startup-library-transition-20261122/result.json), we checked the producer's `metadata_ready` timestamp, not the time the UI later received it. All times below are relative to **that visit's own** initial display/input fence. Negative means the worker had already finished. Font registration was already complete on all three launches.

| Formal visit | Metadata ready | Metadata received | Fonts registered | Controller attachment began | Direct wait for the metadata producer |
| --- | ---: | ---: | ---: | ---: | ---: |
| 1 | −80.903 ms | +4.464 ms | −235.336 ms | +4.467 ms | 0 ms |
| 2 | −97.794 ms | +4.498 ms | −230.548 ms | +4.502 ms | 0 ms |
| 3 | +39.669 ms | +40.213 ms | −229.490 ms | +40.220 ms | 39.669 ms |

Holding the fence, font work and scheduling fixed, making **all** metadata production faster could remove no direct producer wait in the first two visits and at most 39.669 ms in the third. Cache opening is only one part of that production. The slowest of these three launches was visit 1, not visit 3. This is a bound on an observed dependency, not proof that CPU contention cannot change or that a large offline collection behaves the same. Do not combine these three visits with the draw-accounting cohort above.

The [next discriminating experiment](startup-release-draw-20261122/device/INTERPRETATION.md#L17) is two ordinary opens of the **same staged file in different GUI processes**, then a counterbalanced same-file versus equal-bytes/different-file second open. The second comparison tests whether the effect extends beyond general second-open warming. Record card release, metadata-ready, first Library submission and same-frame wall/CPU/fault counters; retain first-frame, exit and restoration safeguards. Do not drop system caches, preload the entire executable, shorten the startup fence or build a second glyph cache. The [release Gray8 tests](startup-release-draw-20261122/README.md#L19) and [shaping comparison](startup-library-transition-20261122/README.md#L51) already argue against spending another round on Library paint micro-optimizations.

**Growing offline caches: a measured code candidate.** [Startup preparation](../../src/app/startup.rs#L169) waits for `CacheManager::open` before publishing the prepared app. At open, [reconciliation](../../src/cache.rs#L2297) holds a SQLite write transaction and walks both artifact trees. Each correctly named leaf performs the same indexed existence query; the current code prepares that statement for each leaf. Keep recovery and the filesystem walk intact; the experiment changes only **prepare once outside the loops, execute once per leaf**.

New `test-env` release microbenchmark: the baseline compiled the full current `src/cache.rs` in a small Rust harness, with the project's `rusqlite` 0.37 and bundled SQLite. The Ubuntu 24.04.5 x86_64 build environment used the host XFS filesystem; Cargo used six jobs. Time only the production `CacheManager::open` call, not process startup, fixture setup or teardown. Each populated fixture had 256 raw and 256 processed buckets, equal raw/processed counts and indexed, valid 1,049-byte PNGs; no pins, aliases, or evictions in timed runs. Fresh process each time, warm OS caches, no cache flush. The baseline-only size sweep (one warmup and 12 samples per size) measured 0.299 ms with no buckets and 2.302 / 4.403 / 12.844 / 22.715 ms with the same 512 buckets and 0 / 1,000 / 5,000 / 10,000 files respectively.

| --- | ---: | ---: | ---: | ---: |
| Empty root | 0.292 ms | 0.270 ms | 0.018 ms | 8/12 |
| 512 empty buckets | 2.237 ms | 2.145 ms | 0.046 ms | 7/12 |
| 1,000 files | 4.280 ms | 2.981 ms | 1.377 ms | 12/12 |

One excluded warmup per arm and size, then six AB and six BA pairs. At 10,000 files the chronological paired savings in ms were 8.561, 13.093, 8.319, 12.793, 14.472, 12.960, 12.942, 12.978, 12.769, 12.399, 12.308 and 13.149. Both arms removed unindexed, unpinned raw/processed orphans, retained a pinned raw orphan with an invalid index entry, and kept indexed processed data in a separate recovery check. There was no meaningful empty-cache result. This is evidence for a small change to **cache opening**, not a 58% reduction in Library startup. Preparation can overlap the first display fence. Measure when metadata actually delays the Library on each device profile before prioritizing this over the ordinary-shelf investigation.

**Does cache size change when the actual desktop Library appears? Yes, on both layouts.** This separate experiment used one retained post-SEND desktop release, not the SQL candidate and not an ELF claimed to be `a38b9b3`. The retained workspace's `cache.rs`, `app/view.rs`, `ui/library.slint` and `Cargo.lock` matched the reviewed copies byte for byte. Start a fresh real application on `test-env` with Winit's software renderer, a private Xvfb display at 1×, and the same non-demo, offline six-book/six-chapter database restored before each process. The books had no artwork; the two fixtures alternated at the same data path. Both had the same 512 buckets; one had zero files, the other 5,000 indexed raw plus 5,000 indexed processed files. No global caches were dropped. Host scheduling was shared, not pinned.

For each layout a reference captured six book title regions plus toolbar, continuation and navigation. Start the host clock immediately before spawning the application; bracket the first byte-equal nine-region match between the start of the last nonmatching capture and the end of the first matching one. This includes process creation and observation delay; it is **not** a card release, a renderer callback, the physical startup fence or an optical measurement. One excluded warmup per arm preceded eight pairs per layout (four in each order); which layout ran first alternated.

| Software layout | Paired median extra time to Library, 10,000 minus 0 files | 10,000 slower by midpoint | Non-overlapping observation brackets | Paired median extra worker-start to prepared-state time |
| --- | ---: | ---: | ---: | ---: |
| Scribe, 930 × 1240 | +24.197 ms | 8/8 | 6/8 | +29.504 ms |
| KPW6, 632 × 840 | +20.482 ms | 8/8 | 7/8 | +25.392 ms |

All paired midpoint differences in ms, in collection order: Scribe `43.862, 16.877, 18.729, 37.503, 4.270, 60.587, 29.664, 5.507`; KPW6 `34.753, 7.983, 14.578, 18.194, 33.305, 43.362, 16.986, 22.769`. The preparation and first-Library intervals overlap; do not add them. This establishes **sensitivity to the number of cached files**, not that a prepared SQL statement recovers the entire difference. Only a same-size control/candidate comparison can establish that. Neither desktop layout substitutes for an installed Kindle.

## How to decide what ships

- On `test-env`, use current control and candidate release builds on **Scribe and KPW6** profiles. Use the [distinct PNG, JPEG, mixed spread, vertical and high-resolution books](../MANUAL_PERFORMANCE_COMICS.md#L8); include Normal single-page as well as Fast two-page. Repeat across fresh processes and both A/B orders. Report per-mode and per-cache-state latency, delivered/requested counts, stale or cancelled requests, peak RSS and next-frame bytes. The three-turn groups above do not support population p95s.
- For a surviving startup candidate, compare actual ordinary card release to the first correct Library (including a correct empty state, without waiting for covers). For Reader, bind input release, app action, draw, framebuffer write and accepted SEND to the same page; report independently observed ink stabilization only if an optical measurement is available. Software deadlines and driver fences cannot substitute for it.
- Require identical output for an unchanged mode, accurate latest-page progress, unchanged refresh and recovery behavior, and no regression under the memory cap. Only after emulator qualification, prepare the guard and fixtures for a bounded Scribe A/B, then acquire the device. Do not promote a host-stage improvement, claim a physical KPW6 result, or replace R3 from these observations alone.
